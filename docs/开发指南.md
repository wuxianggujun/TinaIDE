# TinaIDE 开发指南

> 最后人工核验：2026-08-13

本指南只保留当前代码仍然成立的开发事实，避免继续引用已经过时的流程。

## 项目当前形态

TinaIDE 目前采用 `app + core/* + feature/* + tools/* + external/*` 的模块化结构：

- `app`：应用壳、首页导航、项目编辑器入口、启动流程
- `core/*`：编译、LSP、sysroot、工具链、Git、插件、存储、网络等复用能力
- `feature/*`：编辑器、终端、设置、文件预览、帮助、工作区等用户功能
- `tools/*`：模板 APK、模板公共代码等辅助模块
- `external/*`：本地源码依赖与子模块

后端、管理端和部署运维代码已迁入私有仓库，不再随开源 Android 项目分发。
公开仓库只保留 `server/README.md` 作为边界说明。

默认编译与运行依赖的是：

- `Android sysroot`
- `native tina-toolchain`

可选的 Linux / PRoot 环境不再是基础编译必需项。

## 入口与模块认知

开发时先分清两个主入口：

- `MainPortalActivity`：项目列表、设置、帮助、插件、用户入口
- `MainActivity`：打开项目后的主编辑器工作区

如果你在调试“首页行为”，优先看 `MainPortalActivity`；如果你在调试编辑器 / 文件树 / 构建 / 底部面板，优先看 `MainActivity` 及其 Compose 状态层。

## 开发环境

### 必需

1. Android Studio 最新稳定版
2. JDK 17+
3. Git

### 可选

1. PowerShell 7+
2. Docker Desktop

只有在你需要重建 toolchain / sysroot / rootfs 资产时，Docker 才是必需的。

## 本地启动

### 推荐方式

```powershell
pwsh ./tools/build-apk.ps1 -Install
```

### 常用变体

```powershell
# 模拟器
pwsh ./tools/build-apk.ps1 -Abi x86 -Install

# Release
pwsh ./tools/build-apk.ps1 -Variant release
```

### 直接使用 Gradle

```bash
./gradlew :app:assembleArm64Debug
./gradlew :app:installArm64Debug
./gradlew "-Ptina.devAbi=x86_64" :app:assembleX86_64Debug
./gradlew "-Ptina.devAbi=x86_64" :app:installX86_64Debug
./gradlew :app:assembleDebugAllAbi
./gradlew :app:assembleReleaseAllAbi
```

本地默认只启用一个 ABI 变体：

- 默认 `arm64`
- 通过 `-Ptina.devAbi=x86_64` 切到模拟器 ABI
- 通过 `assemble*AllAbi` 或 `-Ptina.allAbi=true` 恢复双 ABI

## 首次启动与依赖安装

当前默认首次启动流程会进入依赖安装页，并安装：

1. `Android sysroot`
2. `native tina-toolchain`

只有显式进入 Linux 环境相关入口时，才会额外安装：

1. `Linux distro rootfs`
2. `Linux distro runtime metadata`
3. `PRoot guest toolchain`
4. 然后校验 / 安装 `Android sysroot`
5. 然后校验 / 安装 `native tina-toolchain`

对应事实源：

- `StartupFlowManager.kt`
- `DependencyInstallViewModel.kt`
- `AndroidNativeToolchainManager.kt`
- `AndroidSysrootManager.kt`
- `PRootBootstrap.kt`

## 编辑器 / 语言服务开发注意事项

当前编辑器语言服务并不是“所有文件都走 clangd”：

- C / C++：`LspEditorManager` + `LspClientSession`
- CMake：`CMakeLanguageServiceSession`
- Make / `.mk`：`MakeLanguageServiceSession`
- 其他语言：`LspPluginManager` 按插件 manifest 匹配

因此，遇到补全 / 悬停 / 跳转问题时，先确认自己调试的是哪一条路径，不要直接把问题归到 `clangd` 或 `core:lsp`。

### C/C++ 编译上下文诊断

打开 C 或 C++ 文件后，可以点击编辑器底部状态栏的语言服务状态，查看当前标签页实际使用的编译上下文。诊断弹窗按层次展示：

- 本地或远程 clangd 模式及当前连接状态
- `compile_commands.json` 路径、来源、更新时间和项目类型
- 当前文件是精确命中、从相关源文件推断，还是没有匹配的编译命令
- 编译器、C/C++ 标准、Target、工具链、NDK Runtime、Sysroot 和 Clang resource directory
- 头文件搜索路径、预处理宏和完整编译参数

本地 clangd 模式下，弹窗会区分项目或外部工具生成的权威编译数据库与 TinaIDE fallback 数据库。远程模式下，远端编译命令由远程语言服务管理，本机不会伪造远端参数。

遇到“项目可以编译，但 clangd 仍误报”时，建议按以下顺序验证：

1. 查看当前文件是否精确匹配到编译命令。
2. 核对最终 C/C++ 标准、Target、Sysroot、头文件路径和宏是否与真实构建一致。
3. 检查编译数据库来源；外部权威数据库应由 CMake、Bear 或对应构建工具重新生成。
4. 使用弹窗中的“刷新并重载”重新准备编译上下文并连接 clangd。
5. 若仍失败，再结合 LSP 诊断日志定位工具链、Sysroot 或 clangd 启动问题。

### 诊断与 Quick Fix 边界

LSP `Diagnostic` 本身不保证存在自动修复，也没有可靠的“可修复”标志。诊断严重级别、错误码或 `data` 字段都不能用来推测是否应该显示“查看修复”。当前实现遵守以下边界：

- “问题”面板只对当前可见诊断按需请求 `textDocument/codeAction`，并限制最多 2 个并发探测，避免集中请求语言服务器。
- 诊断入口通过 `CodeActionContext.only = [quickfix]` 只请求 Quick Fix；客户端还会过滤服务器误返回的 Refactor / Source Action。
- 只有至少一个 Quick Fix 未被服务器标记为 disabled 时，诊断项才显示“查看修复”。未知、探测中、无修复和请求失败状态都不显示按钮。
- “全部修复”使用当前活动文档的完整 UTF-16 范围请求 `source.fixAll`；只有服务器返回明确 kind 且未 disabled 的 action 时才显示，普通 Command、Quick Fix 或其他 Source Action 不能触发入口。
- 点击“全部修复”时重新请求当前文档版本的 action，不执行后台探测阶段的旧对象；若返回多文件 `WorkspaceEdit`，必须先经过文件数和编辑数预览确认。
- 后台可用性探测失败时保持静默；用户主动打开修复菜单失败时，才显示现有错误提示。
- 编辑器菜单、快捷键和 Host Command 的通用 Code Actions 请求保持不限制 kind，重构与 Source Action 不受诊断入口影响。
- `CancellationException` 必须继续向上传播；不能用未区分取消语义的 `runCatching` 吞掉协程取消。

对应实现位于 `DiagnosticsContent.kt`、`MainActivityBottomPanelHost.kt`、`LspEditorActionsDelegate.kt`、`LspEditorManager.kt` 与 `LspCodeActionService.kt`。

定向回归命令：

```powershell
./gradlew :core:lsp:testDebugUnitTest --tests "com.wuxianggujun.tinaide.core.lsp.LspCodeActionServiceTest" --no-daemon --console=plain
./gradlew :app:testArm64DebugUnitTest --tests "com.wuxianggujun.tinaide.ui.compose.components.DiagnosticQuickFixAvailabilityTest" --no-daemon --console=plain
```

## 返回事件与临时面板

主编辑器中的返回事件按“先关闭临时 UI，再处理页面退出”处理：

1. 已展开的下拉菜单先关闭，不触发页面退出。
2. 底部面板已展开时先收起面板；侧边文件树抽屉打开时由抽屉自己的返回处理优先关闭。
3. 临时 UI 都关闭后，才进入未保存文件退出确认或 Activity 默认返回流程。

菜单统一通过 `core/designsystem` 的 `TinaDropdownMenu` / `TinaExposedDropdownMenu` 注册返回处理；底部面板由 `MainActivityBottomPanelHost` 在抽屉关闭且面板展开时消费返回。修改这些层级时，必须保持上述优先级，避免用户在查看菜单或面板内容时误退出工作区。

## RikkaHub 接入落点

TinaIDE 不再维护内置聊天、渠道、会话仓储和工具调用系统。需要 AI 能力时，
用户从编辑器侧边栏打开内嵌 RikkaHub，并在 RikkaHub 内完成模型、渠道和 API Key 配置。

TinaIDE 侧只维护两个边界：

- `external/rikkahub`：RikkaHub 源码 included build，随默认 Gradle 配置参与构建解析。
- `external/rikkahub/embedded`：把 RikkaHub app 源码和资源包装为 Android library，供 TinaIDE 主 APK 依赖。
- `app/src/main/java/com/wuxianggujun/tinaide/ui/compose/components/DrawerContent.kt`：编辑器侧边栏内嵌 `RikkaHubEmbeddedChatPane`。
- `app/src/main/java/com/wuxianggujun/tinaide/settings/SettingsActivity.kt`：设置页内嵌 `RikkaHubEmbeddedSettingsPane`，并通过 `RikkaHubEmbeddedWarmup` 做宿主侧预热。

RikkaHub 源码适配优先落在 `external/rikkahub` 子模块内；涉及子模块指针更新时，必须先提交并推送 RikkaHub 子模块，再提交主仓库 gitlink。默认静态验证命令：

```powershell
./gradlew :rikkahub:embedded:compileDebugKotlin --offline --build-cache --console=plain --warning-mode all
```

该命令不依赖真机或模拟器。若 Problems report 只剩 `Using a Project object as a dependency notation has been deprecated`，并且 trace 指向 AGP `VariantDependenciesBuilder.createTestComponents`，这是 AGP 9.2.1 创建 Android test component 时触发的内部弃用告警，不应通过批量改写项目依赖声明来规避；后续随 AGP 升级或上游修复处理。

## 帮助文档与仓库文档

App 内帮助中心不是直接读取 `docs/` 目录，而是通过：

- `feature/help/.../HelpRepository.kt`
- `feature/help/src/main/assets/help/*.md`
- `feature/help/src/main/assets/help/en/*.md`

如果你改的是面向 App 内用户的帮助文档，需要同步维护中文与英文 help assets，并保持文件名一一对应；如果你改的是仓库协作文档，则更新 `docs/`。

## 运行资产维护

当前 native 工具链资产不是“手工丢几个压缩包”这么简单，而是受 `current.properties` 约束。

常用入口：

```powershell
# 同步 toolchain / sysroot 资产
pwsh ./tools/sync-tina-toolchain-assets.ps1 -Abi arm64 -Clean
pwsh ./tools/sync-tina-toolchain-assets.ps1 -Abi x86_64 -Clean
```

相关校验：

- `app/build.gradle.kts` 中的 `verifyTinaToolchainAssets`
- `app/src/<abi>/assets/tina-toolchain/current.properties`
- `app/src/<abi>/assets/android-sysroot/*.tar.xz`

## 开发时优先遵守的约束

### 1. 用户可见文案必须走国际化

不要把用户能看到的中文 / 英文直接写进 Kotlin / Java 代码。

优先使用：

- `AppStrings.kt`
- `ResExt.kt`
- `TextResourceAliases.kt`
- `AppResourceAliases.kt`

### 2. 日志统一走项目日志封装

不要在业务代码中直接使用 `android.util.Log`。

当前构建脚本已提供守卫任务：

- `checkNoAndroidUtilLog`

统一使用 `Timber` / `TinaTimber`。

### 3. 模块边界优先清晰

- `feature/*` 尽量只表达用户功能，不互相直接耦合
- `core/*` 提供可复用能力
- `app` 负责装配，而不是继续堆积业务逻辑

### 4. 文档与代码一起改

涉及以下内容时，需要同步更新文档：

- 运行时安装流程
- 模块结构
- 构建命令
- 新增对外能力或删除旧能力

已发布版本区块不再追加开发中变化。Tag 之后的改动先写入 `CHANGELOG.md` 的
`Unreleased`，准备发布时再归档到新的版本号和发布日期。

## Release 构建副作用

当前 Release 相关任务会触发额外行为：

- 自动递增 `version.properties`
- 备份 mapping 文件
- mapping 文件仅由公开构建逻辑做本地归档

因此，Release 构建仍不适合作为“纯只读验证命令”随手执行。若维护者需要外部
symbol 存储集成，应放在公开仓库之外维护。

## GitHub Actions 配置

### PR 自动构建

公开仓库可以直接使用 `pull_request` Workflow 自动构建 Debug APK，**不需要任何密钥**。

- Fork 提交 PR 也可以触发构建
- 产物会作为 artifact 上传
- 这类 Workflow 不要使用 release signing secrets

### Release / Tag 构建

如果你希望公开仓库在 tag 或手动 release 时产出正式 APK，请在 GitHub 仓库的
`Settings -> Secrets and variables -> Actions` 里配置：

- `TINAIDE_RELEASE_KEYSTORE_B64`
- `TINAIDE_RELEASE_KEYSTORE_PASSWORD`
- `TINAIDE_RELEASE_KEY_ALIAS`
- `TINAIDE_RELEASE_KEY_PASSWORD`

说明：

- `TINAIDE_RELEASE_KEYSTORE_B64` 是 `release.jks` 的 Base64 内容
- 其它几项分别对应签名口令和别名
- 这些值只用于 release/tag 构建，不要放进公开代码

### 已废弃：私有仓库派发

旧的“私有仓库构建 -> `repository_dispatch` 派发到公开仓库”流程已经废弃。
当前公开仓库只保留自身的 tag / `workflow_dispatch` 发布入口，不再需要
`TINAIDE_REPO_TOKEN`、`TINAIDE_REPO` 或 `PRO_REPO_TOKEN`。

## 代码提交流程

推荐的最小流程：

1. 修改代码
2. 运行受影响模块的测试或构建任务
3. 更新相关文档
4. 自查用户可见文案、日志、边界和回归点
5. 提交

Commit message 建议继续使用 Conventional Commits，例如：

```bash
git commit -m "docs(readme): align runtime docs with native toolchain flow"
git commit -m "fix(compile): handle missing toolchain metadata"
git commit -m "refactor(editor): split session persistence logic"
```

## 子模块注意事项

仓库包含多个 Git submodule。涉及子模块指针变更时，顺序必须是：

1. 先在子模块仓库提交并推送
2. 再回到主仓库提交子模块指针

否则主仓库 CI 在执行 `git submodule update --recursive` 时可能出现 `not our ref <sha>`。
