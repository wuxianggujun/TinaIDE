# 已知问题

本文基于当前源码整理，尽量只保留现在仍然成立、而且用户确实会遇到的限制与风险点。

## 1. 大型项目性能压力明显

### 现象

- 大型 C/C++ 项目在手机或平板上构建会明显变慢
- clangd 分析大型工程时内存占用较高
- 多个大文件同时打开时，编辑体验可能下降

### 建议

1. 优先使用增量构建
2. 对大型工程考虑使用 **远程 LSP**
3. 不要一次打开过多大文件

## 2. 首次启动与开发环境部署耗时较长

### 现象

- 首次启动或版本升级后，开发环境准备时间可能较长
- 在开发环境尚未就绪前，终端 / 调试 / 构建能力可能不可用

### 建议

1. 首次启动时尽量保持网络稳定
2. 确保存储空间充足
3. 若安装过程异常，进入设置重新部署开发环境

### 旧版本兼容说明

TinaIDE 0.18.22 及更早版本在部分 Redmi / HyperOS 设备上部署 Android sysroot 时，可能提示 `tar entry escapes target directory`。这是系统将 `/data/user/0` 与 `/data/data` 作为同一应用数据目录的路径别名兼容问题，并不表示压缩包一定有问题，也不等同于存储空间不足。

请升级到 0.18.23 或更高版本，再进入设置重新部署开发环境；若升级后仍失败，请导出日志并同时提供设备型号、Android 版本和完整错误信息。

## 3. 外部工作空间与 SAF 在小文件密集场景下会更慢

### 现象

- 外部存储目录通过 SAF 访问时，频繁的小文件操作可能不如内部路径流畅
- 大型仓库或层级很深的工程，目录浏览和扫描可能更慢

### 建议

1. 工作空间尽量保持结构清晰
2. 对频繁构建的项目，尽量避免无关的大量临时文件
3. 出现明显卡顿时，先排查是否是外部存储 I/O 瓶颈

## 4. PRoot / 终端 / 调试链路受设备兼容性影响

### 现象

- 某些 ROM、SELinux 策略或设备环境会影响 PRoot 行为
- 独立终端有时可能启动失败
- LLDB 调试链路在少数设备上可能不稳定

### 建议

1. 遇到启动失败时先重新部署开发环境
2. 先验证普通运行流程，再验证调试流程
3. 保留日志，便于后续定位问题

## 5. 快捷键主要面向硬件键盘

### 现象

- 软键盘往往不能稳定触发 `Ctrl`、`Shift`、`F2` 这类组合键
- 编辑器快捷键在硬件键盘上的体验明显更好

### 建议

1. 把快捷键功能理解为“硬件键盘增强”
2. 若依赖快捷键工作流，优先连接蓝牙或 USB 键盘

## 6. 许可证列表以应用内打包清单为主

### 现象

- 开源许可证页主要展示当前应用依赖与部分打包分发组件
- 个别源码级、原生级子模块可能不会以单独 Maven 条目的形式出现

### 建议

1. 先查看应用内 **开源组件与许可证** 页面
2. 如需核对更底层的源码组件，请同时参考仓库内随附的 `LICENSE` / `NOTICE` 文件

## 7. 系统兼容性边界

### 当前最低要求

- **Android 9.0 / API 28**

### 建议运行环境

- 推荐 **3GB 以上内存**
- 推荐保留足够的可用存储空间，用于工作空间、工具链与构建产物

## 8. 开源版能力与常见疑问

### 在线能力

开源版仍保留插件浏览、插件安装、包下载、收藏、下载历史和 GitHub Release 版本更新提示。

### 私有身份和商业功能

私有身份、商业功能、私有后端和管理端不随公开仓库分发。

### RikkaHub 使用方式

TinaIDE 已移除自研 AI。AI 聊天、模型和渠道配置由内嵌 RikkaHub 提供，请从编辑器侧边栏打开 RikkaHub 后在 RikkaHub 内完成配置。

开发者本地编译时，如果 Gradle Problems report 中出现 `Using a Project object as a dependency notation has been deprecated`，需要先用 `--warning-mode all` 或 deprecation trace 确认来源。若调用栈指向 AGP `VariantDependenciesBuilder.createTestComponents`，这是 Android Gradle Plugin 内部告警，不影响 RikkaHub embedded Kotlin 编译结果。

### 插件市场

开源版市场读取 GitHub Registry。客户端负责浏览、安装和更新插件，不包含私有账号互动和审核流程。

## 9. NDK 共享库模板运行结果看起来像“旧模板”

### 现象

- 新建 NDK 共享库项目后，粘贴新代码
- 编辑器里已经显示新内容
- 点击运行后，控制台还是打印模板测试程序的输出

### 说明

这通常不是“编译器没有重新编译源码”，而是：

1. NDK 共享库模板本来就同时带有共享库目标和测试可执行文件
2. 默认运行配置常常优先指向测试目标
3. 你看到的输出来自测试程序，不一定来自共享库本体

### 建议

1. 先确认文件是否已经保存到磁盘
2. 检查当前运行配置选择的是哪个目标
3. 如果目标是共享库，请切换到 SDL 运行模式或显式选择共享库目标
4. 重新打开项目后高亮恢复，通常说明语言服务重新加载了文件，不代表运行目标自动切换了

### 常见误解

- “我改了源码，运行还是旧的” 不一定是缓存问题
- “高亮能显示新代码” 不等于“当前运行目标就是新代码”
- “重新构建报错了” 也可能只是原先默认跑的目标和你现在想验证的目标不一样

## 10. 构建进程超时或取消后的资源清理

### 说明

构建使用的 CMake、Make、clang 等工具会作为短生命周期进程执行。正常情况下，构建结束、超时或取消后，TinaIDE 会关闭输出流、终止仍在运行的构建进程，并删除本次命令使用的临时目录。

### 不会自动清理的内容

- 项目 `build` 目录
- `compile_commands.json`
- 增量构建缓存
- 已成功生成并注册的 artifact

这些文件属于后续构建和源码变更检测需要复用的持久产物。如果怀疑持久缓存异常，请优先使用“清理构建目录 / 清理并重新配置”，不要手动删除不明确的内部目录。

## 11. raylib 在运行但画面全黑

- 请使用 TinaIDE 0.18.39 或更新版本、raylib 6.0 revision 3 修复包和当前 raylib 模板。
  只升级 TinaIDE APK 不会替换已经安装的 raylib 库；刷新市场并重新安装 raylib 后，
  对测试项目执行“清理并重新配置”，再编译运行。不要为此清除整个 App 的数据。
- revision 1 的已知问题是 `EndDrawing()` 没有执行交换帧、输入轮询和计时；因此
  “EGL 初始化成功”和“循环一直运行”仍可能伴随黑屏。
- revision 2 仍可能在系统侧滑返回后卡住 native 销毁：第一次有画面，第二次运行黑屏，
  重启 IDE 才能再运行一次。revision 3 修复销毁事件循环；新版宿主也会在明确退出后
  回收卡住的独立图形进程，避免它阻塞后续运行。
- 0.18.39 从保存文件开始锁定本次运行请求，快速连点不会排队打开多个窗口。
  如需取消保存后的编译或尚未完成的启动，请使用顶栏独立的停止按钮，再明确发起下一次运行；
  旧编译结果与迟到窗口不会替代新的请求。资源市场的刷新和检查更新也会刷新内存索引，
  不再只清界面缓存；上游版本仍为 `6.0` 时也能发现 revision 3 修复包。
- 游戏正常运行没有总时限。宿主的 2 秒宽限期只用于明确退出后的资源清理，
  不在启动时倒计时，也不因按 Home 或普通切后台而强杀游戏。再次点击“运行”会替换旧会话。
- 更新 IDE 不会修改以前导出的独立 APK。请用新版 IDE 重新导出 raylib/SDL3 项目，
  让独立 APK 也使用单实例入口与明确返回后的退出保护；Home 仍只切后台，不限制游戏运行时间。
- SDL3 项目请更新市场模板到 1.0.4 或更新版本。旧项目若启动时出现半屏，
  应在 `SDL_CreateWindowAndRenderer` 创建时传入 `SDL_WINDOW_RESIZABLE`，
  不要先用 `0` 创建再调用 `SDL_SetWindowResizable`，避免启动时横竖屏请求往返。
- raylib 的 Android 后端没有实现 `GetWindowHandle()`，它返回 `0` 不能说明没有
  原生窗口。应在实际绘制线程检查当前 EGL context、draw surface 和尺寸。
- NativeActivity 的生命周期回调与 raylib 的绘制线程本来就可以不同；不要把绘制
  强行搬到 UI 线程。`InitWindow`、绘制和 `CloseWindow` 应保持在同一 raylib 渲染线程，
  不要直接从新建线程调用绘图 API。
- 验收时同时检查可见动画、触摸响应、快速连点、系统手势返回、返回键退出、连续运行 20 次和后台恢复。
  仍黑屏时请附上最小项目、已安装包的 `packageRevision`、设备 ABI 和本次图形运行日志；
  主进程的 Java 崩溃日志不能替代 NativeActivity 渲染现场。
